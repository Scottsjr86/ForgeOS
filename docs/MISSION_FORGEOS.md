## 0. Mission

ForgeOS exists to turn serious software development into a coherent place the
developer can enter, understand, operate, and advance.

The product must combine the power and precision of a real development
workstation with the spatial clarity, progression, presence, and emotional force
of a great game world.

The permanent mission is:

> Build a developer operating environment in which projects become truthful,
> explorable worlds; software capabilities become earned progression; real tools
> remain authoritative; and a bounded AI companion helps the developer move from
> intent to proven behavior without losing control of the system.

ForgeOS must make ambitious software easier to reason about, easier to continue,
and more satisfying to build.

It must not merely make development look futuristic.

It must make development work better.

---

## 1. The problem ForgeOS solves

Modern software development is powerful but fragmented.

A developer may need to coordinate:

- source repositories;
- editors;
- terminals;
- build systems;
- test runners;
- debuggers;
- language servers;
- Git branches and worktrees;
- architecture documents;
- issue trackers;
- AI conversations;
- coding agents;
- patches;
- logs;
- release requirements;
- remembered project rules;
- unfinished work from previous sessions.

Each tool may work well in isolation while the complete development experience
remains scattered across windows, files, chats, dashboards, and human memory.

AI coding increases this pressure.

Code can now be produced faster than a developer can safely preserve:

- architectural intent;
- source authority;
- dependency direction;
- proof of actual capability;
- regression boundaries;
- current project context;
- a reliable answer to what should happen next.

Traditional development environments primarily organize work around files,
windows, tasks, or commits.

ForgeOS organizes work around the software being built:

```text
project
  -> release destination
  -> capability graph
  -> active mission
  -> current blocker
  -> bounded source change
  -> real tool execution
  -> user-observed behavior
  -> earned capability
```

The central product question is not:

> Did code change?

It is:

> What can this software truthfully do now, and what is the next safe move?

## 2. Permanent destination

The permanent destination is a complete Linux-based spatial developer operating
environment.

The developer boots into ForgeOS and enters a persistent command environment in
which:

- projects occupy memorable places;
- capability trees expose what the software can and cannot do;
- architecture and repository boundaries are visible;
- real editor, terminal, Git, build, test, and debugging surfaces remain fast;
- active work appears as a bounded mission;
- blockers interrupt progression honestly;
- agents operate inside explicit authority;
- Nyx remains present as a project-aware technical companion;
- proof and regression state shape the environment;
- completed releases become durable project history;
- normal Linux applications remain available when needed.

The final experience should evoke operating advanced technical armor with an
intelligent partner at the developer's side.

That experience must be earned through functionality.

The permanent progression is:

```text
real Linux development workstation
  -> truthful project cockpit
  -> persistent capability world
  -> supervised agent foundry
  -> complete spatial developer operating system
```

The armor must work before it glows.

## 3. Product identity

ForgeOS is all of the following together:

### 3.1 A developer operating environment

ForgeOS is the primary place from which the developer opens projects, edits
source, runs commands, inspects Git state, builds, tests, debugs, works with AI,
and advances releases.

### 3.2 A project operating system

ForgeOS holds a persistent model of:

- projects;
- repositories;
- releases;
- capabilities;
- prerequisites;
- active work;
- blockers;
- experiments;
- proof;
- invalidation;
- workspace state.

### 3.3 A spatial interface

ForgeOS uses a game-engine-powered world to provide orientation, memory,
relationships, state, and presence.

The spatial layer is not decoration pasted over an IDE.

It is a truthful projection of project state.

### 3.4 A proof-driven development environment

ForgeOS treats a capability as earned only when the real product path works,
required negative behavior is correct, regressions remain locked, and the user
has exercised and approved the behavior within the active version's scope.

### 3.5 An AI-assisted command environment

`nyx_server` hosts local models, remote-agent access, tool routing, permissions,
checkpoints, context assembly, and run audit.

Nyx helps the developer understand and operate ForgeOS.

Nyx is not the authority that decides the project is correct.

### 3.6 A serious workstation first

ForgeOS must support long, ordinary development sessions.

The developer must be able to forget the spectacle and simply work.

The system must remain useful when:

- visual effects are disabled;
- voice is disabled;
- remote AI is disabled;
- the network is unavailable;
- the user prefers keyboard control;
- the user remains in flat coding mode for hours.

## 4. Intended user

ForgeOS is initially built for developers who:

- build ambitious software alone or in small teams;
- use Linux;
- work across large or long-lived repositories;
- use local or remote AI coding tools;
- care about architectural authority and regression safety;
- need persistent project context across sessions;
- want visible progression without fake productivity metrics;
- enjoy game-like spatial systems but refuse to sacrifice real efficiency;
- are willing to use a new development environment when it provides genuine
  operational value.

The first user is the ForgeOS developer.

ForgeOS must be built from inside ForgeOS as early as the active version allows.

The first credible proof of product value is not a promotional video.

It is ForgeOS becoming the preferred environment for continuing ForgeOS itself.

## 5. Core product promise

The complete product promise is:

> Boot into ForgeOS, enter a project, understand its real state, select a valid
> next capability, work manually or with Nyx and bounded coding agents, execute
> real tools, review the result, and advance the project only when the behavior
> actually works.

The V1 promise is narrower:

> Boot into ForgeOS and complete real Rust development work without leaving the
> ForgeOS session for an external IDE.

That V1 journey includes:

```text
boot ForgeOS
  -> open a real repository
  -> inspect and edit source
  -> use a terminal
  -> run registered project commands
  -> inspect Git state
  -> ask Nyx for project-aware help
  -> optionally dispatch one bounded heavyweight coding task
  -> review and accept or reject the returned patch
  -> run formatting, build, and tests
  -> commit a verified change
```

V1 is not required to deliver the complete spatial fantasy.

V1 is required to prove that the development environment is real.

## 6. The ForgeOS experience

ForgeOS should feel powerful because the system is understandable and responsive,
not because the screen is always busy.

The intended experience has two complementary layers.

### 6.1 Operational layer

The operational layer contains the high-density surfaces used for actual work:

- code editor;
- terminal;
- search;
- diagnostics;
- Git status and diff;
- build and test output;
- debugger;
- documentation;
- Nyx conversation;
- agent patch review.

These surfaces must remain precise, legible, low-latency, keyboard-accessible,
and conventionally useful.

### 6.2 Spatial layer

The spatial layer provides:

- project identity;
- project navigation;
- capability relationships;
- repository and subsystem boundaries;
- architecture topology;
- mission context;
- build, test, and process state;
- agent presence;
- release progression;
- historical continuity.

The spatial layer may compress, reveal, connect, animate, and contextualize real
state.

It may not invent it.

### 6.3 Adaptive intensity

ForgeOS should change its presentation according to the work.

During focused coding, the environment should become quiet and flat.

During architecture review, spatial relationships may expand.

During debugging, runtime paths and related diagnostics may become prominent.

During release closure, capability and proof state may dominate the environment.

The developer should feel that the system forms around the current task rather
than forcing every task through one theatrical layout.

## 7. Nyx mission

Nyx is the resident technical companion of ForgeOS.

Nyx exists to reduce context loss, operational friction, and avoidable mistakes
without taking project authority away from the developer.

Nyx should eventually be able to:

- explain the current project state;
- identify the active repository and mission;
- search and read source;
- explain diagnostics and command output;
- operate approved tools;
- preserve project context across sessions;
- prepare bounded work for local or remote agents;
- monitor long-running operations;
- request explicit approval at permission boundaries;
- return exact results and uncertainty;
- help diagnose blockers;
- recommend valid next work from the canonical router;
- remain quiet when no help is needed.

Nyx must never:

- fabricate source or tool state;
- hide uncertainty;
- award skill closure;
- expand its authority silently;
- treat generated prose as proof;
- bypass user approval;
- replace Forge Core project truth;
- become a second hidden workflow authority.

The desired relationship is not master and autonomous servant.

It is developer and bounded technical copilot inside a system whose truth remains
inspectable.

## 8. Capability progression mission

ForgeOS does not treat activity as progress.

Progress is not awarded for:

- lines written;
- prompts sent;
- time spent;
- commits created;
- files generated;
- animations completed;
- tests weakened until green;
- documentation claiming completion;
- agents reporting success.

Product progression is earned when:

```text
capability statement
  -> prerequisites satisfied
  -> real path exercised
  -> first blocker resolved
  -> mechanical behavior locked
  -> negative behavior correct
  -> regressions preserved
  -> user-facing path functional
  -> user exercises and approves behavior
  -> closure records completed
  -> capability closed
```

The capability tree exists to keep destination, dependency, and truth visible.

It must never become a second issue tracker filled with disconnected tasks.

## 9. Version mission

ForgeOS advances through four bounded versions.

### 9.1 V1: First Armor

Mission:

> Earn a raw but real bootable ForgeOS development environment capable of daily
> Rust work and one bounded Nyx-assisted agent workflow.

V1 proves usability.

V1 must not be delayed by V2 world systems, V3 autonomy, or V4 cinematic polish.

### 9.2 V2: Living Forge

Mission:

> Turn projects into persistent truthful worlds with selectable capability trees,
> missions, experiments, proof, history, native developer surfaces, and multiple
> supported language profiles.

V2 proves project awareness.

### 9.3 V3: Autonomous Foundry

Mission:

> Allow Nyx to coordinate bounded local and remote agents, multi-repository work,
> experiments, invalidation, CI, and project archaeology while the human remains
> final authority.

V3 proves supervised autonomy.

### 9.4 V4: Aegis Ascendant

Mission:

> Deliver the complete spatial developer operating system with a persistent
> Jarvis-like Nyx presence, adaptive project worlds, normal Linux application
> integration, and a polished advanced-command-theater experience.

V4 earns the complete product vision.

No version may claim the mission of a later version before its own launch gate is
closed.

## 10. V1 mission boundary

The active mission is ForgeOS V1: First Armor.

V1 must establish:

- a dedicated ForgeOS Linux session;
- a reliable ForgeOS shell;
- a project registry and restorable workspace;
- repository-safe file access;
- a real editor workflow for Rust;
- embedded terminal sessions;
- registered formatting, build, and test commands;
- real Git inspection and mutation;
- managed `nyx_server` lifecycle;
- local-model project assistance;
- exact approval resume for bounded Nyx operations;
- one bounded OpenAI heavyweight-agent workflow;
- patch intake, review, acceptance, rejection, and safe application;
- truthful command and status presentation;
- recovery from declared process or shell failures;
- installation and boot on a clean supported host;
- one real ForgeOS or Nyx feature completed from inside ForgeOS.

V1 is allowed to be visually raw.

V1 is not allowed to be functionally fake.

The following are explicitly later-version work unless required to remove a V1
blocker:

- full capability-world rendering;
- complete mission gameplay;
- multi-agent orchestration;
- broad language support;
- architecture districts and project archaeology;
- natural voice as a primary interface;
- multiplayer collaboration;
- marketplace systems;
- virtual reality;
- custom Wayland compositor;
- fully cinematic project worlds.

## 11. What ForgeOS must never become

ForgeOS must not become:

### 11.1 A normal IDE with a science-fiction skin

If the spatial layer can be removed without changing how the project is
understood, ForgeOS has not earned its larger identity.

### 11.2 A game that happens to contain a text editor

If the user must fight the world to perform normal development work, the product
has failed.

### 11.3 An AI wrapper

ForgeOS must retain value without remote AI and must not reduce the product to a
chat panel around existing tools.

### 11.4 A replacement for proven development tools

ForgeOS orchestrates Git, compilers, language servers, debuggers, formatters,
test runners, shells, and Linux.

It does not reproduce them badly to claim ownership.

### 11.5 An autonomous agent laboratory with the developer removed

The developer remains the authority for scope, approval, product judgment, and
release acceptance.

### 11.6 A documentation-driven simulation of progress

Documents define intent and authority.

Real behavior earns completion.

### 11.7 A permanent prototype

Each version must ship as a bounded usable product.

The permanent dream may be enormous.

The active release must remain finite.

## 12. Product values

### 12.1 Truth before spectacle

Every important visual state must resolve to inspectable source-owned state or a
real tool result.

### 12.2 Control before autonomy

Automation expands only after permission, observability, rollback, and review are
strong enough to bound it.

### 12.3 Local-first before cloud dependence

Core development remains available locally.

Remote models and services enhance the system but do not become its foundation.

### 12.4 Integration before replacement

Use existing tools through explicit contracts before considering a replacement.

### 12.5 Cohesion before breadth

One complete, coherent workflow is worth more than twenty disconnected features.

### 12.6 Recoverability before cleverness

A failed process, model, shell, patch, or command must leave the project in a
known recoverable state.

### 12.7 User approval before declared completion

A source path may be technically proved while still being unusable.

The user must exercise and approve every skill before it is closed.

### 12.8 Architecture before accumulation

New code must strengthen the declared system rather than create another path
around it.

### 12.9 Efficiency before ceremony

ForgeOS must reduce operational friction.

Workflow rules exist to protect source and truth, not to manufacture paperwork.

### 12.10 Ambition without self-destruction

The complete vision remains active, but each version must be small enough to
finish and strong enough to stand on its own.

## 13. Product success

ForgeOS succeeds when developers voluntarily choose to remain inside it because
it makes real work more coherent, understandable, safe, and satisfying.

V1 success means:

- ForgeOS boots reliably;
- the developer can complete ordinary Rust work;
- Nyx is useful without being dangerous or theatrical;
- real commands and Git state remain trustworthy;
- one real ForgeOS feature is completed entirely inside ForgeOS;
- the developer prefers continuing development inside ForgeOS over immediately
  returning to an external IDE.

Long-term success means:

- project state remains understandable across months or years;
- capability progression reflects real behavior;
- AI agents can contribute without dissolving project authority;
- the spatial environment improves orientation instead of slowing work;
- ForgeOS supports extended daily use;
- the final command-theater experience feels earned rather than decorative.

Commercial success is compatible with the mission but cannot override it.

ForgeOS must be worth paying for because it is a powerful development
environment, not because essential project state is held hostage.

## 15. Final mission statement

ForgeOS will make software development feel like operating a living technical
system rather than juggling disconnected tools.

It will preserve the rigor of real engineering while restoring a sense of place,
progression, presence, and wonder.

Nyx will stand beside the developer as a bounded technical intelligence.

The project world will change because the software changed.

Capabilities will illuminate because they were earned.

The final experience will feel like coding inside advanced armor in a spatial
command theater.

But every panel, light, mission, agent, and world state must trace back to
something real.

```text
V1 earns the workstation.
V2 earns the living project.
V3 earns the foundry.
V4 earns the armor.
```

The armor must work before it glows.
